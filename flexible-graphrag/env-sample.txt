# Entity-name de-duplication (CocoIndex pipeline only), applied to one

# Single CocoIndex refresh cadence in seconds (default 60).  Change detection is

# This interval is used as the BACKUP cadence in three places:
#   * localfs walk_dir(rescan_interval=…) — periodic full rescan that catches any
#     file-system events the watcher missed,
#   * the restart backoff if a live stream ends/errors,
#   * the reconcile poll for sources with NO change stream (native S3/Azure/Drive
#     scan connectors; flexible web / wikipedia / youtube / cmis).
# Set to 0 to disable the backup poll for non-change-aware sources.

#COCOINDEX_POLL_INTERVAL=0

# Per-stage Postgres monitoring — writes rows to cocoindex_ingest_log (one row per stage per file).
# Observability only; does NOT drive change detection or incremental sync.
# Requires POSTGRES_INCREMENTAL_URL (same DB as incremental updates — see section below).
# Two tables are created automatically:
#
#   cocoindex_run_log — one row per update cycle (startup/ui/poll/live).
#     adds / deletes / unchanged / reprocesses / errors are DOCUMENT counts.
#     (CocoIndex's own totals sum every component it ran — the per-file worker plus
#     parse plus embed plus one KG extraction per CHUNK — so a single 5-chunk file
#     would read as "adds=8".  These columns are filtered to the per-file components;
#     the raw per-component breakdown is kept in the "note" column.)
#     Live-mode rows appear when a file is added/deleted from the watch folder, making
#     watch-folder changes fully visible without a UI.
#     Query example:
#       SELECT trigger, adds, deletes, unchanged, errors, elapsed_s, logged_at
#       FROM cocoindex_run_log ORDER BY logged_at DESC LIMIT 20;
#
#   cocoindex_ingest_log — per-file rows, driven by the pipeline progress hook.
#     Only fires for files that actually ran (memo hits and pure deletes emit nothing).
#     Query example:
#       SELECT trigger, file_path, stage, status, detail, logged_at
#       FROM cocoindex_ingest_log ORDER BY logged_at DESC LIMIT 50;
#
# Row volume for cocoindex_ingest_log (COCOINDEX_MONITOR_DETAIL):
#   summary (default) — ONE row per file: the terminal event with its status
#                       (completed / skipped / failed) and detail.
#   stages            — a row per stage transition (~13 per file):
#                       downloading→downloaded→parsing→parsed→chunked→embedded→
#                       kg_extracting→kg_extracted→vector_indexing→graph_indexing→
#                       search_indexing→rdf_indexing→indexing_complete→done
#                       Use when debugging where a file stalls; it swamps the table
#                       on a real corpus.

#COCOINDEX_MONITOR_DETAIL=stages
#COCOINDEX_ENABLE_PG_MONITORING=false
#COCOINDEX_ENABLE_PG_MONITORING=true

# Generates synonyms/related keywords to improve KEYWORD/BM25 recall.

#   "Acme staff" and "Acme employees" are different BM25 queries — synonyms fix this.
#

#   Vector stores (LI + LC) use embedding similarity — the model handles synonyms
#   implicitly. Explicit expansion just multiplies vector calls with little gain.
#   LI PropertyGraph seeds entity lookup via vector search — same reasoning.
#   Graph QA chains (RDF, Cypher) fire a full LLM call per synonym — N cycles =
#   N near-duplicate answers and N× latency.

#   langchain_vector            — LC vector store      [not recommended — same reason]
#   llamaindex_pg_graph         — LI PropertyGraph VectorContextRetriever [not recommended]
#   langchain_pg_vector         — LC PG entity vector retriever
#   langchain_pg_neighborhood   — PG neighborhood k-hop retriever
#   langchain_rdf_graph         — LC RDF/SPARQL retriever  [AVOID — N LLM cycles per synonym]
